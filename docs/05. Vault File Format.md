# ĐẶC TẢ ĐỊNH DẠNG TỆP TIN VAULT - SECURE VAULT MANAGER (SVM)

---

## 1. Cấu Trúc Thư Mục Kho Dữ Liệu (Vault Directory Layout)

Để đáp ứng khả năng lưu trữ các tệp đính kèm lớn (Attachments), lịch sử phiên bản (Item History) và snapshot sao lưu tức thời, mỗi Vault được cấu trúc thành một **thư mục độc lập** trong vùng dữ liệu người dùng (`$XDG_DATA_HOME/secure-vault-manager/vaults/<vault_id>/` trên Linux, `%LOCALAPPDATA%\secure-vault-manager\vaults\<vault_id>\` trên Windows, hoặc `~/Library/Application Support/secure-vault-manager/vaults/<vault_id>/` trên macOS):

```text
vaults/<vault_id>/
├── vault.svm               # Tệp nhị phân chính: Chứa Header, KDF params, Wrapped DEK và Ciphertext các Items
├── vault.svm.lock          # File lock tránh xung đột khi có nhiều tiến trình mở đồng thời
├── biometric.env           # (Tùy chọn) Phong bì DEK phục vụ mở khóa sinh trắc học qua OS Keychain/TPM
├── attachments/            # Thư mục lưu trữ các tệp đính kèm đã được mã hóa riêng biệt
│   ├── <attachment_id>.blob
│   └── ...
└── backups/                # Thư mục chứa các snapshot sao lưu tự động xoay vòng
    ├── vault.20261103_165000.svm
    └── ...
```

## 2. Đặc Tả Nhị Phân Tệp `vault.svm`

Tệp `vault.svm` được tổ chức thành 2 phân vùng rõ rệt: **Unencrypted Header** (kích thước cố định **112 bytes** chứa siêu dữ liệu cần thiết để phục vụ KDF giải mã) và **Encrypted Payload** (chứa toàn bộ cơ sở dữ liệu các mục lưu trữ).

```text
+-------------------------------------------------------------------------+
| UNENCRYPTED HEADER (Cố định 112 bytes: 24 + 12 + 60 + 16 bytes)         |
+-------------------------------------------------------------------------+
| Magic Bytes: "SVM1" (4 bytes ASCII: 0x53, 0x56, 0x4D, 0x31)             |
| Format Version: 0x0001 (2 bytes uint16 little-endian)                   |
| Flags: 2 bytes reserved (0x0000, giữ cố định)                           |
| Salt: 16 bytes ngẫu nhiên từ CSPRNG                                     |
+-------------------------------------------------------------------------+
| KDF Parameters Block (Argon2id) (12 bytes)                              |
|   - Memory Size (m_cost): uint32 little-endian (ví dụ: 65536 = 64MiB)   |
|   - Iterations (t_cost): uint32 little-endian (ví dụ: 3)                |
|   - Parallelism (p_cost): uint32 little-endian (ví dụ: 4)               |
+-------------------------------------------------------------------------+
| Wrapped DEK Envelope Block (60 bytes)                                   |
|   - Envelope Nonce: 12 bytes ngẫu nhiên (ChaCha20-Poly1305)             |
|   - Encrypted DEK: 32 bytes (Data Encryption Key)                       |
|   - Poly1305 Tag: 16 bytes Authentication Tag                           |
+-------------------------------------------------------------------------+
| Payload Metadata (16 bytes)                                             |
|   - Payload Nonce: 12 bytes ngẫu nhiên                                  |
|   - Reserved: 4 bytes (0x00000000)                                      |
+-------------------------------------------------------------------------+
| ENCRYPTED PAYLOAD (Độ dài N bytes)                                      |
+-------------------------------------------------------------------------+
| Ciphertext: Dữ liệu JSON danh sách VaultItem nén Zstandard (zstd)       |
| Poly1305 Authentication Tag: 16 bytes cuối cùng                         |
+-------------------------------------------------------------------------+
```

### 2.1. Cơ Chế Xác Thực Associated Data (AAD)

Khi thực hiện mã hóa và giải mã khối Payload, toàn bộ **112 bytes** từ đầu tệp đến hết phần Payload Metadata (toàn bộ Unencrypted Header) được sử dụng làm **Associated Data (AAD)** trong thuật toán AEAD ChaCha20-Poly1305. Bất kỳ sự thay đổi trái phép nào đối với Magic Bytes, Salt, KDF Parameters hoặc Wrapped DEK đều khiến quá trình giải mã Payload thất bại ngay lập tức trước khi phân tích cú pháp dữ liệu.

### 2.2. Cơ Chế Lưu Trữ Khóa Sinh Trắc Học (`biometric.env`)

Để giữ cho cấu trúc Header và dữ liệu xác thực **AAD (112 bytes)** của tệp `vault.svm` luôn cố định và độc lập, tính năng sinh trắc học được lưu trữ tại tệp đồng hành `biometric.env`:

1. Khi kích hoạt (`svm_vault_biometric_enable`), hệ thống sinh một khóa ngẫu nhiên **Biometric Wrapping Key (BWK)** 32 bytes và lưu trữ vào phân hệ bảo mật của OS (macOS Keychain với `kSecAccessControlBiometryCurrentSet`, Windows Hello / DPAPI, hoặc Linux Polkit/SecretService).
2. Bản sao của `DEK` được mã hóa bằng `BWK` (ChaCha20-Poly1305) và ghi vào tệp `biometric.env` (60 bytes: 12B Nonce + 32B Encrypted DEK + 16B Tag) nằm cạnh tệp `vault.svm`.
3. Trạng thái sinh trắc học được nhận diện trực tiếp dựa trên sự hiện diện của tệp `biometric.env` và khóa trong OS Keychain. Nhờ đó, việc bật hoặc hủy kích hoạt (`svm_vault_biometric_disable`) chỉ đơn giản là tạo hoặc xóa tệp `biometric.env` cùng khóa trong Keychain mà **hoàn toàn không làm biến đổi AAD hay đòi hỏi mã hóa lại Payload** của `vault.svm`.

## 3. Đặc Tả Tệp Đính Kèm An Toàn (`attachments/*.blob`)

Các tệp đính kèm có thể có dung lượng từ vài KB đến 50MB. Để tối ưu hóa bộ nhớ RAM và bảo mật tối đa:

1. Mỗi tệp đính kèm được sinh một khóa riêng **Attachment Key (AK)** ngẫu nhiên 32 bytes.
2. Khóa AK được mã hóa bằng **DEK** và lưu trữ dưới dạng siêu dữ liệu trong thuộc tính của `VaultItem`.
3. Nội dung tệp được mã hóa theo giao thức **STREAM AEAD** (kích thước chunk 64 KiB) sử dụng thuật toán ChaCha20-Poly1305:

```text
+-------------------------------------------------------------------------+
| ATTACHMENT BLOB HEADER (16 bytes)                                       |
+-------------------------------------------------------------------------+
| Magic Bytes: "SVMB" (4 bytes)                                           |
| Chunk Size: 0x00010000 (4 bytes = 65536 bytes)                          |
| Base Nonce Prefix: 7 bytes ngẫu nhiên từ CSPRNG                         |
| Reserved: 1 byte (0x00)                                                 |
+-------------------------------------------------------------------------+
| STREAM CHUNKS (Mỗi chunk = Encrypted Data + 16 bytes Poly1305 Tag)      |
+-------------------------------------------------------------------------+
| Chunk 0: Encrypted Data (64 KiB) + Tag (16 bytes)                       |
| Chunk 1: Encrypted Data (64 KiB) + Tag (16 bytes)                       |
| ...                                                                     |
| Final Chunk: Encrypted Data (<= 64 KiB) + Tag (16 bytes)                |
+-------------------------------------------------------------------------+
```

### Cấu Trúc Nonce & Xác Thực AAD Cho Từng Chunk STREAM

- **Cấu trúc Nonce 12-byte cho Chunk thứ `i`:**
  `Nonce = Base Nonce Prefix (7B) || Block Counter (4B Big-Endian) || Final Flag (1B)`
  Trong đó `Final Flag` bằng `0x00` cho các chunk trung gian và `0x01` cho chunk cuối cùng của tệp.
- **Dữ liệu xác thực AAD cho Chunk thứ `i`:**
  `AAD = vault_id (UUID 36B) || attachment_id (UUID 36B) || chunk_index (uint32 BE)`
  Việc gắn chặt `vault_id` và `attachment_id` vào AAD đảm bảo kẻ tấn công không thể tráo đổi các blob giữa các tệp đính kèm hoặc thay đổi thứ tự các chunk mà không bị phát hiện.

## 4. Quản Lý Ghi Đĩa, Sao Lưu & Đồng Bộ

### 4.1. Quy Trình Ghi Nguyên Tử (Atomic Write)

Để chống lại hiện tượng hỏng tệp khi mất nguồn đột ngột, mọi thao tác ghi `vault.svm` đều tuân thủ:

1. Ghi dữ liệu ra tệp tạm thời `vault.svm.tmp.<pid>`.
2. Gọi hàm `fsync()` để đẩy toàn bộ dữ liệu từ OS page cache xuống đĩa cứng vật lý.
3. Đổi tên nguyên tử (`atomic rename`) tệp tạm đè lên `vault.svm`.
4. Gọi `fsync()` trên thư mục cha (`vaults/<vault_id>/`) để cập nhật directory entry trên Linux/macOS.

### 4.2. Chính Sách Xoay Vòng Bản Sao Lưu (Backup Retention)

Trước mỗi lần thực thi các tác vụ rủi ro (Import dữ liệu, sửa đổi hàng loạt), hệ thống tự động copy snapshot `vault.<YYYYMMDD_HHMMSS>.svm` vào thư mục con `backups/`. Hệ thống tự động duy trì tối đa **05 bản sao lưu gần nhất** và xoay vòng xóa các bản cũ hơn.

### 4.3. Tương Thích Đồng Bộ Tệp Cục Bộ (Syncthing / Nextcloud)

SVM không tích hợp cloud riêng nhưng hỗ trợ người dùng đặt thư mục lưu trữ trên các công cụ đồng bộ tệp như Syncthing hoặc Nextcloud:

- Hệ thống lắng nghe các tệp xung đột do công cụ đồng bộ sinh ra (ví dụ: `vault.sync-conflict-*.svm`).
- Khi phát hiện tệp xung đột, ứng dụng không tự ý ghi đè mà phát tín hiệu `SVM_EVENT_ITEMS_CHANGED` thông báo cho người dùng trên UI để kiểm tra và giải quyết xung đột thủ công.
